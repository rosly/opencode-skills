# Topic 08 — Advanced and Complementary Techniques

## 1. Property-based testing (PBT)

- SOURCE FACT (Rank 1) — The origin is QuickCheck: "QuickCheck is a tool which aids the Haskell programmer in formulating and testing properties of programs" and "Properties are described as Haskell functions, and can be automatically tested on random input" ([Claessen & Hughes, QuickCheck, ICFP '00, ACM](https://dl.acm.org/doi/10.1145/351240.351266)).
- SOURCE FACT (Rank 1) — QuickCheck claims component-level random testing covers behavior well: "When a function is built from separately tested components, then random testing suffices to obtain good coverage of the definition under test" ([Claessen & Hughes, QuickCheck, ICFP '00, ACM](https://dl.acm.org/doi/10.1145/351240.351266)).
- SOURCE CLAIM (Rank 3) — The key PBT idea is to state properties rather than individual examples: "instead of writing individual test cases (eg unit tests corresponding to input-output pairs for particular functions) one should write properties that are desired of the functions, and then automatically generate random tests which can be run to verify (or rather, falsify) the property" ([UPenn CIS 5520 QuickCheck lecture](https://www.cis.upenn.edu/~cis5520/current/lectures/stub/05-quickcheck/QuickCheck.html)).
- SOURCE CLAIM (Rank 2) — Example-based suites are the baseline PBT is contrasted with: "The tests that we typically write today can be classified as example-based tests. They explicitly specify the inputs and outputs we want to use and observe" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE CLAIM (Rank 2) — PBT is positioned as complementary, not a replacement: "it should not be viewed as a substitute for traditional example-based testing. Instead, it should be used in conjunction with example-based testing as a complementary approach" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE CLAIM (Rank 2) — Generator bias toward bugs is deliberate: "The aim of property-based testing is not to generate random data for its own sake, but specifically to generate data which finds bugs" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE CLAIM (Rank 2) — Counterexample reduction is a distinguishing feature: "Counterexample shrinking is an essential component in this, and is unique to property-based testing frameworks" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE CLAIM (Rank 2) — Randomness need not be flaky: "Property-based testing with fast-check can be made fully deterministic by setting a constant `seed` value" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE CLAIM (Rank 2) — PBT also documents intent: "By writing property-based tests, you capture the essence of what the code should do" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE CLAIM (Rank 2) — Fuzzing is framed as a sub-case: "Fuzzing is the idea of firing lots of randomly generated values onto an algorithm to find bugs. In a way, it's not that far from property-based testing and can even be considered a sub-case of it" ([fast-check, Why Property-Based Testing](https://fast-check.dev/docs/introduction/why-property-based/)).
- SOURCE FACT (Rank 1) — Empirical value: a study of 30 experienced practitioners reports "PBT's main strengths lie in testing complex code and in increasing confidence beyond what is available through conventional testing methodologies" and its "main weaknesses ... lie in the relative complexity of writing properties and random data generators and in the difficulty of evaluating their effectiveness" ([Goldstein et al., Property-Based Testing in Practice, ICSE 2024](https://dl.acm.org/doi/10.1145/3597503.3639581)).
- SOURCE FACT (Rank 1) — Practitioners still mix methods: "example-based tests were written to test complementary functionality that could not be easily tested with properties" ([Goldstein et al., Property-Based Testing in Practice, ICSE 2024](https://www.cis.upenn.edu/~bcpierce/papers/icse24-pbt-in-practice)).
- SOURCE FACT (Rank 1) — PBT can be more bang per test: "on average, each property-based test kills about 50 times as many mutants as the average unit test" ([An Empirical Evaluation of Property-Based Testing in Python, PACMPL 2025/2026](https://dl.acm.org/doi/10.1145/3764068)); the same abstract limits scope: "The results from our study may be primarily applicable to property-based testing in the Python language" ([same](https://dl.acm.org/doi/10.1145/3764068)).
- AI INFERENCE — PBT extends example-based TDD by replacing hand-picked input/output pairs with universally quantified properties plus generation; its cost is the specification and generator effort, so it complements rather than replaces example-based cycles. The mutant-kill ratio is relative to mutants generated by one language's mutation operators and one study's corpora, so it should not be read as a general multiplier.

## 2. Mutation testing

- SOURCE FACT (Rank 1) — Definition and status: "Mutation Testing is a fault-based software testing technique that has been widely studied for over three decades" ([Jia & Harman, An Analysis and Survey of the Development of Mutation Testing, IEEE TSE 37(5), 2011](https://ieeexplore.ieee.org/document/5487526)).
- SOURCE FACT (Rank 1) — Its scoring criterion: "Mutation testing is a fault-based testing technique which provides a testing criterion called the 'mutation adequacy score'" ([Jia & Harman, IEEE TSE 2011, abstract contents](https://ieeexplore.ieee.org/document/5487526)).
- SOURCE CLAIM (Rank 3) — Mechanism: "Mutation testing involves making small changes to the program being tested. Each changed version is called a *mutant*" and "Rejection is called *killing* the mutant. The value of a test suite is measured by the percentage of mutants that it kills" ([Wikipedia, Mutation testing, rev. 6 Sep 2026](https://en.wikipedia.org/wiki/Mutation_testing)).
- SOURCE CLAIM (Rank 3) — Mutants model realistic faults: mutation operators "either mimic typical programming errors (such as using the wrong operator or variable name) or force the creation of valuable tests" ([Wikipedia, Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)).
- SOURCE CLAIM (Rank 3) — Foundation hypotheses: "The first is the *competent programmer* hypothesis" and "The second hypothesis is called the *coupling effect*" ([Wikipedia, Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)).
- SOURCE CLAIM (Rank 3) — Adequacy conditions: "A test must *reach* the mutated statement"; "Test input data should *infect* the program state"; "The incorrect program state ... must *propagate* ... and be checked by the test"; "These conditions are collectively called the *RIP model*" ([Wikipedia, Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)).
- SOURCE CLAIM (Rank 3) — The core practical obstacle: "Such mutants are called *equivalent mutants*" and "Equivalent mutants detection is one of the biggest obstacles to practical usage of mutation testing" ([Wikipedia, Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)).
- SOURCE CLAIM (Rank 3) — A mutation score is not simply "detected": "if a mutant is not detected by the test suite, this typically indicates that the test suite is unable to locate the faults represented by the mutant, but it can also indicate that the mutation introduces no faults" ([Wikipedia, Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)).
- SOURCE CLAIM (Rank 3) — Cost historically limited adoption: "This problem of the expense of mutation testing had reduced its practical use as a method of software testing" ([Wikipedia, Mutation testing](https://en.wikipedia.org/wiki/Mutation_testing)).
- AI INFERENCE — Mutation testing is the "test the tests" complement to TDD: it gives a fault-detection adequacy signal that coverage does not. Its limits are equivalent/subsumed mutants and compute cost. A high mutation score still depends on the mutation operators chosen and does not prove absence of faults. The strongest external validity claim (are mutants a substitute for real faults?) is not established here — see Open questions.

## 3. Code coverage metrics and their limits

- SOURCE CLAIM (Rank 3) — Coverage measures execution, not checking: "Test coverage is a useful tool for finding untested parts of a codebase. Test coverage is of little use as a numeric statement of how good your tests are" ([Martin Fowler, Test Coverage, 17 Apr 2012](https://martinfowler.com/bliki/TestCoverage.html)).
- SOURCE CLAIM (Rank 3) — Targets are gamed: "The trouble is that high coverage numbers are too easy to reach with low quality testing" ([Martin Fowler, Test Coverage](https://martinfowler.com/bliki/TestCoverage.html)).
- SOURCE CLAIM (Rank 3) — Suspicion of 100%: "I would be suspicious of anything like 100% - it would smell of someone writing tests to make the coverage numbers happy, but not thinking about what they are doing" ([Martin Fowler, Test Coverage](https://martinfowler.com/bliki/TestCoverage.html)).
- SOURCE CLAIM (Rank 3) — Only low coverage is clearly diagnostic: "Certainly low coverage numbers, say below half, are a sign of trouble. But high numbers don't necessarily mean much" ([Martin Fowler, Test Coverage](https://martinfowler.com/bliki/TestCoverage.html)).
- SOURCE CLAIM (Rank 3) — Fowler quotes Brian Marick: "If a part of your test suite is weak in a way that coverage can detect, it's likely also weak in a way coverage can't detect" ([Martin Fowler, Test Coverage](https://martinfowler.com/bliki/TestCoverage.html)).
- SOURCE FACT (Rank 1) — Large empirical study: "We found that there is a low to moderate correlation between coverage and effectiveness when the number of test cases in the suite is controlled for. In addition, we found that stronger forms of coverage do not provide greater insight into the effectiveness of the suite" ([Inozemtseva & Holmes, Coverage Is Not Strongly Correlated with Test Suite Effectiveness, ICSE 2014](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)).
- SOURCE FACT (Rank 1) — Conclusion drawn: "coverage, while useful for identifying under-tested parts of a program, should not be used as a quality target because it is not a good indicator of test suite effectiveness" ([Inozemtseva & Holmes, ICSE 2014](https://dlnext.acm.org/doi/pdf/10.1145/2568225.2568271)).
- SOURCE FACT (Rank 1) — Confound: "Since coverage is increased by adding code to existing test cases or by adding new test cases to the suite, the coverage of a test suite is correlated with its size" ([Inozemtseva & Holmes, ICSE 2014](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)).
- SOURCE CLAIM (Rank 3) — Coverage is about the test procedure, not code quality: "code coverage helps you understand the quality of your test procedures, not the quality of the code itself" ([Software Engineering Stack Exchange, Is test coverage an adequate measure of code quality?](https://softwareengineering.stackexchange.com/questions/192/is-test-coverage-an-adequate-measure-of-code-quality)).
- AI INFERENCE — The key limitation: coverage records which code was *executed*, not whether results were *checked* or whether the checked behavior is correct. It is therefore useful as a gap-finding instrument (locating unexecuted code) and dangerous as a target metric; high coverage can coexist with assertion-free or weak tests. Mutation testing, by requiring a detectable behavior change, is the stronger adequacy signal in the sources above.

## 4. Contract testing

- SOURCE CLAIM (Rank 2) — Definition: "***Contract testing** is a technique for testing an integration point by checking each application in isolation to ensure the messages it sends or receives conform to a shared understanding that is documented in a "contract"*" ([Pact docs, Introduction](https://docs.pact.io/)).
- SOURCE CLAIM (Rank 2) — Purpose: "Contract tests assert that inter-application messages conform to a shared understanding that is documented in a contract" and without them the only alternative is "expensive and brittle integration tests" ([Pact docs, Introduction](https://docs.pact.io/)).
- SOURCE CLAIM (Rank 2) — Consumer-driven shape: "Pact is a code-first *consumer-driven* contract testing tool ... The contract is generated during the execution of the automated consumer tests" ([Pact docs, Introduction](https://docs.pact.io/)).
- SOURCE CLAIM (Rank 2) — Contract-by-example vs schema: "a Pact contract is enforced by executing a collection of test cases, each of which describes a single concrete request/response pair - Pact is, in effect, 'contract by example'" ([Pact docs, Introduction](https://docs.pact.io/)).
- SOURCE CLAIM (Rank 2) — Scope discipline: "Use Pact for contract testing, not functional testing of the provider" ([Pact docs, Writing Consumer tests](https://docs.pact.io/consumer)).
- SOURCE CLAIM (Rank 2) — Only used interactions are fixed: "only parts of the communication that are actually used by the consumer(s) get tested ... any provider behaviour not used by current consumers is free to change without breaking tests" ([Pact docs, Introduction](https://docs.pact.io/)).
- SOURCE CLAIM (Rank 3) — Fowler's framing: contract tests "check that all the calls against your test doubles return the same results as a call to the external service would" ([Martin Fowler, Contract Test, 12 Jan 2011](https://martinfowler.com/bliki/ContractTest.html)).
- SOURCE CLAIM (Rank 3) — Cadence differs from unit tests: "These tests need not be run as part of your regular deployment pipeline ... these tests need to be based on the rhythm of changes to the external service" ([Martin Fowler, Contract Test](https://martinfowler.com/bliki/ContractTest.html)).
- SOURCE CLAIM (Rank 3) — Origin of the pattern: "the article then describes the 'Consumer-Driven Contract' pattern, which imbues providers with insight into their consumer obligations" ([Ian Robinson, Consumer-Driven Contracts, 12 Jun 2006, hosted by Martin Fowler](https://martinfowler.com/articles/consumerDrivenContracts.html)).
- AI INFERENCE — Contract testing extends TDD across a service boundary: each side is tested in isolation against a shared, versioned contract instead of against the live counterpart. It substitutes for slow integration tests and for drift between a provider and its documented schema, but it intentionally does not test provider business logic or end-to-end behavior.

## 5. Approval / golden-master / characterization testing

- SOURCE CLAIM (Rank 3) — Definition and provenance: a characterization test "(also known as Golden Master Testing) is a means to describe (characterize) the **actual** behavior of an existing piece of software, and therefore protect existing behavior of legacy code against unintended changes via automated testing. This term was coined by Michael Feathers" ([Wikipedia, Characterization test, rev. 10 Sep 2026](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 3) — It inverts assertion style: "Traditional tests check that individual properties have certain values (whitelists them), whereas characterization testing checks that no properties have been changed (blacklisted)" ([Wikipedia, Characterization test](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 3) — It is a change detector, not a correctness oracle: "characterization tests do not verify the *correct* behavior of the code ... Instead they verify the behavior that was observed when they were written" ([Wikipedia, Characterization test](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 3) — Safety-net value: "They enable, and provide a safety net for, extending and refactoring code that does not have adequate unit tests" ([Wikipedia, Characterization test](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 3) — Best for large/unstructured outputs: "It is generally a sensible approach for complex results such as PDFs, XML, images, etc. where checking all relevant attributes with assertions would be both insensible ... and result in unreadable/unmaintainable test code" ([Wikipedia, Characterization test](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 3) — Core limitation: "Golden Master testing does not imply correctness of the results. It merely helps detect unwanted effects of software changes" ([Wikipedia, Characterization test](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 3) — Determinism dependency: "It depends on repeatability. Volatile and non-deterministic values need to be masked / removed" ([Wikipedia, Characterization test](https://en.wikipedia.org/wiki/Characterization_test)).
- SOURCE CLAIM (Rank 4) — Tooling definition: "Approvals work by comparing the test results to a golden master. If no golden master exists you can create a snapshot of the current test results and use that as the golden master" ([ApprovalTests package page, PyPI](https://pypi.org/project/approvaltests/)).
- SOURCE CLAIM (Rank 6) — Practitioner origin of "approval tests": Llewellyn Falco introduced the term in 2008: "Approval Tests (a pictures worth a 1000 tests)" ([Llewellyn Falco, blog, 13 Oct 2008](http://llewellynfalco.blogspot.com/2008/10/approval-tests.html)); the concept is also "referred to as characterization tests, golden master tests, snapshot tests, locking tests, and sometimes even regression tests" ([NS-Techblog, TDD and legacy code, 29 Jan 2024](https://medium.com/ns-techblog/tdd-and-legacy-code-creating-a-snapshot-with-approval-tests-252327b6c72e)).
- SOURCE CLAIM (Rank 6) — Approval is a deliberate human act, and blanket re-approval destroys value: "Approves bugs as readily as correct behaviour — the snapshot records what is, not what should be" and "Blanket re-approval after a failure is quick, tempting, and destroys the entire value of the technique" ([Approval Testing — Next-Gen Test Methods](https://test.apispi.com/methods/approval-testing)).
- AI INFERENCE — Approval/golden-master testing complements TDD for legacy or output-heavy code where per-field assertions are impractical: capture observed output, review and approve it, then treat any future diff as a regression alarm. Because the approved artifact encodes current behavior (including bugs), it must be re-derived by careful human review, and it must sit on deterministic output.

## Open questions

- UNKNOWN — Are mutants a valid substitute for real faults? The frequently cited Just et al. study ("Are mutants a valid substitute for real faults in software testing?") was not fetched in this round; its result is not asserted here.
- UNKNOWN — Quantitative thresholds for mutation score, and whether mutation score should be used as a quality target, given that coverage-as-target is empirically criticized (Inozemtseva & Holmes). No authoritative threshold was located.
- UNKNOWN — How much of PBT's "50x mutant kill" finding (single-language empirical study) transfers to statically typed or non-Python ecosystems.
- UNKNOWN — Contract testing's relationship to the broader "test doubles" taxonomy; Fowler's bliki distinguishes contract tests from ordinary doubles but the boundary with integration tests in practice was not fully specified by the fetched sources.
- UNKNOWN — Whether approval/golden-master tests should be retained after refactoring. Falco's 2008 post suggests removal after refactoring ("But after you are done safely refactoring, you can/should remove the tests"), while other sources treat them as durable regression tests; this tension was not resolved.
- Open design question for TDD integration — none of the fetched sources define a single prescribed ordering for combining example-based TDD, PBT, mutation testing, contract testing, and approval testing; they present them as complementary techniques with different oracles and cadences.
